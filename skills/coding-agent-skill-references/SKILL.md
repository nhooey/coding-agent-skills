# Skill references and preferences

_A skill names another skill by its bare name and lists every one it names in a closing Related skills section. Its user's personal choices live in a preferences file beside it, never in the skill._

## Name a skill by its bare name

Refer to another skill only by its bare name in backticks: `` `coding-agent-route-feedback-to-skills-over-memory` ``. Never a URL, an owner, a repo or a path to its folder.

A bare name resolves to whatever copy of that skill is installed. Someone who forks the collection gets their own copies of the related skills, and the names in every SKILL.md then point at those, with no edit. A URL would pin every fork to the original.

## The Related skills section

Every skill named anywhere in a SKILL.md body is listed in a closing `## Related skills` section, which opens on exactly this intro, then one bullet per skill:

```markdown
## Related skills

When one of these applies and it's in your skill listing, load it
without asking. If it isn't in your listing, tell the user which skill is
missing and ask whether to install it from the same collection this skill
came from; don't apply it from memory.

- `<name>`: <what it covers, one line>
```

The section is the last in the file. A skill named in the body but missing from it, or listed but never relevant, is a defect to fix in the same edit.

## Loading related skills

When a skill you load lists related skills:

- **Installed and applies:** load it without asking. Its listing already put it in front of you; asking only slows the turn.
- **Missing:** tell the user which skill is missing and ask whether to install it from the same collection the listing skill came from. Installing changes the skills of every session, not just this one, so it is the user's call.
- **Never from memory:** don't apply a missing skill from what you recall of it. Your recollection may be stale or from another fork, and nothing tells the user it happened.

## Relationships go in the body

Frontmatter fields Claude Code doesn't know are ignored, and the model never sees the frontmatter beyond `name` and `description`. A `related:` or `requires:` field would reach neither the agent nor the user, so relationships between skills go in the body, in the Related skills section, where the agent reads them.

## Preferences files

A skill's defaults are written for anyone. A user's personal choices, a wording, an order, a glyph, a default they picked, live in a preferences file named after the skill, next to the installed skill's folder in the agent-neutral `.agents/skills/` folder:

| Scope   | Path                                                   | Managed by                                        |
| ------- | ------------------------------------------------------ | ------------------------------------------------- |
| User    | `~/.agents/skills/<skill-name>.preferences.md`         | the user's Home Manager config                    |
| Project | `<project>/.agents/skills/<skill-name>.preferences.md` | the project's repo, committed like any other file |

A project's file overrides the user's, and the user's overrides the skill's defaults. `~/.claude/skills` links to `~/.agents/skills`, and `<project>/.claude/skills` to `../.agents/skills`, so the same files serve every agent. Agent Skills discovery ignores loose files in a skills folder, since only a subfolder holding a SKILL.md is a skill, so a preferences file is never mistaken for one.

**Why beside the skill, not inside it:** the installed skill folder is read-only, a Nix store path, and is replaced on every update; an edit inside it would be lost or refused. Keeping the file outside also lets a fork's users keep their own preferences against any copy of the skill.

**Who writes them:**

- **Project file:** edit it in the project and commit it with the change it belongs to.
- **User file:** don't write it directly. It is generated by the user's Home Manager config, so a direct write is overwritten on the next switch; propose the change to that config instead.

## The "Your preferences" section

A skill that supports preferences carries this section, just before Related skills, with its own name in place of `<skill-name>`:

```markdown
## Your preferences

!`cat "${CLAUDE_SKILL_DIR}/../<skill-name>.preferences.md" "${CLAUDE_PROJECT_DIR}/.agents/skills/<skill-name>.preferences.md" 2>/dev/null || true`

If your agent doesn't run the line above, read these files yourself if they
exist: `<skill-name>.preferences.md` next to this skill's folder, then
`.agents/skills/<skill-name>.preferences.md` in the project. A project's
file overrides the user's, and the user's overrides this skill's defaults.
```

Claude Code runs the line that opens on an exclamation mark when it loads the skill and puts the files' contents in its place, the user's first and the project's after it, so the later one wins where they differ. Another agent sees the line as text, and the paragraph under it tells it to read the same files itself.

## Which feedback goes where

When the user corrects how a skill works:

- **A lesson right for anyone using the skill:** edit the skill. A gotcha, a missing edge case, a rule every user would want.
- **A personal choice:** put it in that skill's preferences file, the project's or the user's by where it should hold. Editing the skill would force it on everyone who installs it.

`coding-agent-route-feedback-to-skills-over-memory` covers the routing in full: when a lesson goes into a skill rather than memory, and how to propose the edit.

## When to apply

- Writing or editing a SKILL.md that names another skill, or that should read a preferences file.
- Loading a skill whose Related skills section lists others.
- Deciding where a correction about a skill belongs: the skill, or its preferences file.

## Related skills

When one of these applies and it's in your skill listing, load it
without asking. If it isn't in your listing, tell the user which skill is
missing and ask whether to install it from the same collection this skill
came from; don't apply it from memory.
